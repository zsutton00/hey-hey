# Run and Turn Lifecycle

### description

The lifecycle model for the CLI's agent runtime — the layer that owns a long-lived agent session, its provider (Claude SDK, Codex), and every user-message turn that flows through it. See @[design_doc:85aa0c6e-5d39-4887-9da1-a856f823af41|Run & Turn Lifecycle] for the full specification.

**Concepts**

- **Session** (`AgenticSession`) — the persisted record. Owns `agentic_session_id`, `conversationId`, `contextMetadata`, `provider`, and `provider_session_id`. Session has no `promptType` — prompt type is not a session concept.
- **Run** — the long-lived unit of work anchored to an `agentic_session_id`. Owns the Session (held as a field, fetched once at Run activation), the provider session, the conversation, `isProcessing`, the current `(externalAgentNodeId, triggerMessageId)` trigger context (rotated only as an atomic pair from an agent-node dispatch — see invariant 14), the message queue, an append-only report chain, and at most one active Turn. Run is the scheduler: it resolves all Turn inputs, constructs a fully-formed Turn, and reacts to Turn completion to drain the queue. Run does not own `promptType` — that arrives with the trigger and belongs to the Turn.
- **Turn** — one user-message → assistant-complete cycle with three explicit phases. `begin()` / `run()` / `end()` operate exclusively on Turn-owned fields: `resolvedPrompt`, `handler`, `processingMessageId`, `externalAgentNodeId`, `triggerMessageId`, `runnerChoice`, `abortController`. A Turn is immutable once constructed and holds no reference to its Run.
- **Handler** — a pure data declaration per `promptType`: how to build a prompt, what submission tools are allowed, how to transform output, what to do on completion. Resolved once before Turn construction and carried on the Turn as a non-null field.
- **Provider Session** — the SDK's internal conversation/config, owned by the Run for the Run's lifetime. Anything configured at session start must remain valid for the whole Run.
- **Submission-tool Registry** — HTTP MCP endpoint keyed on a Run-scoped token. The dictionary entry (tools, `parentMessageId`, `externalAgentNodeId`) is mutable per Turn; the token is not.
- **Workflow Service boundary** — server-authoritative. The CLI tracks only the active Run's current `externalAgentNodeId`; the server owns node transitions.

**Lifecycle initiation**

Run creation and termination are initiated by **signed envelopes from the API**, not by direct local-HTTP calls from the UI. This decouples Run lifecycle from the device hosting the UI: any authenticated client can start or stop a Run, and the API routes the command over the same machine-addressed signed channel established by @[feature:5bd98aa4-f136-4146-88f7-3042432e95ce|CLI Channel Security].

- **Start.** A user-initiated start posts to the API, which authors a SYSTEM trigger message carrying an `AgentTriggerStartRun` variant and emits a `SignedConversationTriggerEnvelope` to the user's connected CLI. The CLI's dispatcher creates the Run as if `createRun` had been called locally — same Session resolution, same provider-session opening, same Turn construction.
- **Stop.** A user-initiated stop posts to the API, which emits a signed control envelope (see CLI Channel Security) to the owning CLI. The dispatcher calls the active Run's abort path.

The local `POST /api/local/runs` and `POST /api/local/runs/:id/stop` routes are no longer the user-facing entry points. Run identity, Session ownership, and the Turn lifecycle invariants below are unchanged — only the initiation transport differs.

**Input admission**

Every executable input a Run receives enters through one durable, per-machine admission queue before the Run sees it. That includes a user's start or follow-up, an executable workflow trigger, and a collaboration request from another Agent Session. Each queue record keeps the input's identities separate: the operation or trigger key and its fingerprint, the admission, the source message, and the Turn identity chosen at pickup.

- **Admit before acknowledging.** The CLI writes each verified input to the queue before it acknowledges delivery, so an input the platform counts as delivered survives a CLI restart. A duplicate delivery of the same identity returns the recorded acknowledgement instead of creating new work. A different fingerprint under the same identity is rejected.
- **Pick up in order, one at a time.** For each Agent Session, the oldest queued input is picked up only when its Run can accept work: no active Turn, no queued Turn, no foreground child wait and no pending scope review. Pickup assigns the Turn identity. The Run stays the scheduler, and each admitted input becomes its own Turn; admitted inputs are never merged.
- **Report execution status.** For each user input, the queue's acknowledgement records whether the admitted input runs now or has to wait (see @[task:6ba63be9-cbdb-488c-a80d-4728fcc93d36|Return the actual input disposition in the submission response]), and the queue reports status changes to the platform against the same message: `queued` only when the input has to wait, `started` when execution begins, `cancelled` or `failed`. Reports are revisioned, so a retried or delayed report never moves a message backwards. These reports drive the message queue in @[feature:f4fc9bf0-75b0-4365-84b1-c532d827f0ea|Agent Session UI].
- **Cancel only before pickup.** A cancellation request for a queued input reaches the CLI as a signed control command and is serialized with pickup. If cancellation wins, the input is marked cancelled and never executes, even after a replay or restart. If pickup already won, the Turn proceeds and the request reports `started`. Stopping a running Turn is a separate path.
- **Settle and recover.** When a Turn settles, the queue records its terminal evidence and delivers any collaboration result to the requesting session. After a process restart, an input that started but never settled is settled as aborted, without calling the provider again.
- **Work only on unfinished inputs.** Every queue record is kept so replays and early cancellations are always recognized, but only unfinished records get attention. The queue keeps a durable list of the sessions that still have unfinished inputs. At startup it reads only those sessions. After that, a session is advanced only when its own inputs change, when its Run becomes able to take input, or when a failed delivery or status report is due for retry. The one permitted pass over every stored session happens at startup, and only when that list is missing, unreadable or of an unsupported version, for example on the first start after upgrading. Because the list is derived from the session records, rebuilding it once from those records is the only way to find unfinished work safely. Treating a lost list as empty would strand queued and started inputs. This satisfies the Scaling requirement.

**Idle reaping**

An idle run reclaims its runtime footprint without losing continuity. When a run goes idle with an empty queue, it arms a per-run inactivity timer; the timer refreshes on each new turn and is cleared on stop and cleanup, so a processing or stopped run is never reaped. On expiry — and only while the run is still genuinely idle (no active Turn, empty queue, not processing) — the run releases its live provider session and is evicted from the in-memory registry, freeing both its memory and the held provider connection. Because `provider_session_id` stays persisted, the next incoming message re-materializes the run and resumes against that session via `ResumeRunner`, with no loss of conversation continuity. A run-lived runner that cannot release its session surfaces an error rather than silently skipping the reap. The inactivity interval is configurable, with a default applied when unset. Reaping is purely a runtime-liveness concern: it never touches `AgentSession.status`, which is user-owned bookkeeping.

**Session bootstrap**

Participating runs begin with a shared pre-run investigation step before the main agent's first turn (see @[design_doc:ffe9ab11-043a-487d-9781-6eab9c926ef6|Session bootstrap: shared pre-run investigation engine]):

- **Procedural context pre-fetch.** The run procedurally fetches `get_context` for its focal entity before the first agent turn — no agent turn is spent on it. On bootstrap failure this procedural context is what the run falls back to.
- **Bootstrap investigation agent.** The first agent the Run executes — through the standard Run/Turn machinery, not a side-channel sub-agent — runs exactly once per Run with a read-only toolset (enforced by toolset definition) and produces a structured `Frame` describing the focal entity's surrounding graph. The bootstrap prompt is singular across session types; each participating prompt-type handler supplies a situation descriptor (session type, the main agent's toolset, what the session must produce) that the prompt consumes. The agent decides its own investigation depth — there are no handler-declared depth tiers.
- **Run-scoped Frame.** The Frame is held as run-scoped, local-only state: injected into the first turn of each agent subsequently started within the run, never re-injected into turns that continue a provider session that already received it, and never persisted to the platform.
- **Model selection.** The bootstrap runs on the user-selected model and reasoning effort per the @[feature:295ef834-d7d5-45ed-8e76-986ec7385bb1|Agent Sessions] model-selection contract — no pinned internal model.
- **Failure degradation.** If the bootstrap fails, the run proceeds with the procedural context only and the degradation is logged with its cause; a failing bootstrap never blocks a session.
- **Visibility.** Bootstrap messages post to the session conversation through the standard posting path; there is no dedicated UI surface or event channel.
