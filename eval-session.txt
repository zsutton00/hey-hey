## What "relevant surrounding graph" means

Take a task that reads _"add a button that calls `POST /widget` with `{ type: "widget", title }`"_. Read literally it is a button and a fetch; inside a project it is rarely only that. The button may inherit the design system's component and accessibility conventions; the endpoint may return a `processingId` — making the action _pending_, pulling in an "in progress" toast and a contract for resolving the result; `type: "widget"` may trigger a backend Step Function with its own lifecycle. Any, all, or none of these hold — your job is to surface which, from the requirements, contracts, and design docs that already own those decisions, not to guess and not to reverse-engineer them from code.

Relevance is judgment, not a checklist. A node earns a place in the frame only when the analysis would be poorer without it. Examples of the kind of connection worth pulling in:

- **A UI task sitting under a backend feature.** The structural parent is backend, but the work is frontend, so the project's UI-practices feature carries the conventions that actually apply. Pull that UI-practices feature in (or, if it's a sprawling design doc, extract just the slice that applies and mark the node `contentSource: 'extracted'`) so the frame surfaces the rules the implementation will be judged against.
- **A backend task that defines an API.** Walk to the consuming frontend feature whose contract the task must satisfy. The frame should show the consumer, not just the producer, so the analysis can talk about whether the proposed shape actually serves the caller.
- **A task that supersedes a prior one.** Pull in the predecessor (and its design doc if it carries the decisions being reversed) so the analysis can speak to what's changing and why, instead of presenting the new work in isolation.

These are illustrations of the move, not the only shapes that qualify. The discipline is the same in every case: a connection earns space when removing it would degrade the analysis.

### description

## Current state and user attention

Agent Session surfaces compose two concepts. They never treat Run phase, Agent Session current state, and output attention as three competing signals.

| Concept                      | Scope                                      | Values and examples                                                                                                                                                                                                                                                        | Resolution                                                                                                       |
| ---------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Shared session current state | One effective value shared across users    | Ordinary execution: `IDLE`, `STARTING`, `THINKING`, `WRITING`; handler-owned active modes such as `REVIEWING`; blocking override: `AWAITING_APPROVAL`; shared actionable terminal states: `PLAN_READY`, `IMPLEMENTATION_READY`, and future workflow-owned readiness states | A Run transition, approval settlement, new Turn, or completion of the workflow action that owns a terminal state |
| User attention               | One typed value per user and Agent Session | `NONE`, informational `MESSAGE_READY`, and future user-specific attention kinds such as `COMMIT_READY`                                                                                                                                                                     | That user opens, acknowledges, or otherwise satisfies the attention policy                                       |

@[feature:6fd245bc-6474-49ee-8d0a-1d013095db8b|Run Current State] owns the effective active Turn state. Conversation-scoped phase delivery and Agent Session-keyed `currentState` delivery are projections of that same state, not independent product concepts. Session surfaces consume the canonical Agent Session `currentState`; they do not render or rank a conversation phase beside it.

Shared actionable terminal states express that the session or workflow still needs action and remain until that action resolves. User attention expresses whether one user has seen a result. `MESSAGE_READY` is the generic informational completion marker: it may coexist with any shared current state, including a later Turn's active state, and opening the session may clear it only for that user. Clearing user attention never changes shared current state. Clicking changes shared current state only when the click performs the state-resolving workflow action.

## User Interactions

**Context access.** When a session is attached to an entity, the session surface keeps that entity reachable throughout the conversation. The attachment is part of session scope, not a prompt-only detail.

**Interaction model.** Users can send follow-up messages at any time, including while the agent is mid-turn or its CLI is offline. Each message is saved once. A message the agent can take straight away is not shown as queued; one that has to wait behind earlier work shows as queued until the agent starts on it. Either way, it moves into the conversation only when the agent starts on it. Queued messages run one turn each, in the order they were sent. A queued message can be cancelled until the agent starts on it, and it shows as cancelled only once the CLI confirms the cancellation. The queue survives reloads and CLI restarts.

**Read-only fallback.** When a session's runtime is unavailable, the user can still open the session and read the conversation history. Runtime-dependent controls are withheld until the session can be driven again.

analysis: I researched your question — can an errored eval attempt be automatically retried twice, with the successful retry used in the comparison — against Agent Evaluations and the records around it. As currently specified, this is a deliberate non-goal, so it is a change of direction rather than a gap.

    **What the graph says**
    - The design doc @[design_doc:8a7aed78-e688-4d4e-8fc4-8b58c36df034|In-App Agent Evaluations] rules it out: "The runner does not try to rescue a stuck or failing attempt. Intervening would change the conditions of the attempt being measured. An error is recorded against its attempt and the other attempts continue; rerunning is a new attempt the user chooses to start." It also says not to centre the design on automatic retries, and lists "automatic retries" among the deferred items. The design doc is READY and is linked to the feature as both DEPENDS_ON and DERIVES_FROM.
    - The feature requirements say the same. Errors stay beside the affected attempt, and independent attempts continue. Errored and stopped repeats are "named and left out of averages". Setup comparison is "correct out of finished attempts" with reported counts. Nothing in the feature, the Contract or the mockups mentions retry. @[task:24aa8d29-3219-4d0e-b3dc-62ffdc7d1fce|Agent Evaluations] has no requirement that fulfils a retry.
    - The nearest shipped answer is repeats (@[task:a0556f25-88ec-48b6-a3b7-3111e9730364|Let an eval run repeat each case and setup several times, and summarise the repeats], COMPLETED). It addresses variance, not errors. Repeats are fixed at launch (1–10), and "adding more to a finished run is out of scope". A user whose attempt errored today must start a new run by hand, which is the pain in the request.

    **Constraints a retry would hit**
    - @[contract:afba3989-faf6-4776-ae15-ddbc8fb11b9b|Eval run launch] guarantees one EVAL_ATTEMPT per case, setup and repeat, with the attempt report id as the attempt's identity. Start is accepted only with the run id and every recorded attempt, and recorded inputs never change after launch. The CLI admission contract @[contract:917e9c8b-9eeb-4d22-8d71-a71ac549040d|Run Eval handler admission] is the other side of the same boundary. A retry must either live inside one recorded attempt (several provider sessions under one attempt) or create unrecorded attempts. The second breaks the "exactly the recorded attempts" promise, so the first is the only consistent shape. That choice is not made anywhere.
    - The runner is a fixed procedure, not an agent, and each attempt is a fresh inert Run in its own prepared Agent Session and Conversation. Each retry would be a new session. Per-attempt records (human review, judge assessment, usage, cost, provider sessions, tool calls) are all keyed to one attempt and one session. These records are shown in @[task:8523946b-98c8-4346-8f00-7b3b92ed97b8|Show what each eval attempt cost, read from ccusage after it settles] and related tasks. The graph does not say which session or sessions a retried attempt reports.
    - "Use the successful retry in the comparison" means the failed first try is left out of the averages. Measurement says costs and tokens are attributed to each attempt and that partial values are labelled. Dropping failed tries hides the cost of the failures, and a configuration that errors often looks as good as one that does not. The requirements are silent on whether the discarded tries stay visible.
    - Which errors count is not settled. The design separates user stops and time/token limit stops, which are not errors. Judging and measurement failures also exist (for example the Codex token-measurement bug and the missing-session-file behaviour that fails an attempt). Retrying a hard failure (invalid configuration, handler that cannot start as the first agent) would only repeat it.
    - The run page, statuses and mockups would need a retry representation. Current statuses are QUEUED, RUNNING, JUDGING, COMPLETED, ERROR and STOPPED, and the mockups show no retry state or setting.

    **Contract and diagram candidates**
    No new Contract candidate. If retry is adopted, the change belongs inside Eval run launch (recorded settings) and the attempt record. The graph holds no Diagram specific to this, beyond the Eval UX Flow and Eval Batch Run diagrams, which I did not read.

    **For the handler**
    A retry would reverse a recorded design decision, not fill a missing detail. The in-app description of the feature should be checked before any behaviour is promised. ⎿ I researched your question — can an errored eval attempt be automatically retried twice, with the successful retry used in the comparison — against Agent Evaluations and the records around it. As currently specified, this is a deliberate non-goal, so it is a change of direction rather than a gap.

**What the graph says**

- The design doc @[design_doc:8a7aed78-e688-4d4e-8fc4-8b58c36df034|In-App Agent Evaluations] rules it out: "The runner does not try to rescue a stuck or failing attempt. Intervening would change the conditions of the attempt being measured. An error is recorded against its attempt and the other attempts continue; rerunning is a new attempt the user chooses to start." It also says not to centre the design on automatic retries, and lists "automatic retries" among the deferred items. The design doc is READY and is linked to the feature as both DEPENDS_ON and DERIVES_FROM.
- The feature requirements say the same. Errors stay beside the affected attempt, and independent attempts continue. Errored and stopped repeats are "named and left out of averages". Setup comparison is "correct out of finished attempts" with reported counts. Nothing in the feature, the Contract or the mockups mentions retry. @[task:24aa8d29-3219-4d0e-b3dc-62ffdc7d1fce|Agent Evaluations] has no requirement that fulfils a retry.
- The nearest shipped answer is repeats (@[task:a0556f25-88ec-48b6-a3b7-3111e9730364|Let an eval run repeat each case and setup several times, and summarise the repeats], COMPLETED). It addresses variance, not errors. Repeats are fixed at launch (1–10), and "adding more to a finished run is out of scope". A user whose attempt errored today must start a new run by hand, which is the pain in the request.

**Constraints a retry would hit**

- @[contract:afba3989-faf6-4776-ae15-ddbc8fb11b9b|Eval run launch] guarantees one EVAL_ATTEMPT per case, setup and repeat, with the attempt report id as the attempt's identity. Start is accepted only with the run id and every recorded attempt, and recorded inputs never change after launch. The CLI admission contract @[contract:917e9c8b-9eeb-4d22-8d71-a71ac549040d|Run Eval handler admission] is the other side of the same boundary. A retry must either live inside one recorded attempt (several provider sessions under one attempt) or create unrecorded attempts. The second breaks the "exactly the recorded attempts" promise, so the first is the only consistent shape. That choice is not made anywhere.
- The runner is a fixed procedure, not an agent, and each attempt is a fresh inert Run in its own prepared Agent Session and Conversation. Each retry would be a new session. Per-attempt records (human review, judge assessment, usage, cost, provider sessions, tool calls) are all keyed to one attempt and one session. These records are shown in @[task:8523946b-98c8-4346-8f00-7b3b92ed97b8|Show what each eval attempt cost, read from ccusage after it settles] and related tasks. The graph does not say which session or sessions a retried attempt reports.
- "Use the successful retry in the comparison" means the failed first try is left out of the averages. Measurement says costs and tokens are attributed to each attempt and that partial values are labelled. Dropping failed tries hides the cost of the failures, and a configuration that errors often looks as good as one that does not. The requirements are silent on whether the discarded tries stay visible.
- Which errors count is not settled. The design separates user stops and time/token limit stops, which are not errors. Judging and measurement failures also exist (for example the Codex token-measurement bug and the missing-session-file behaviour that fails an attempt). Retrying a hard failure (invalid configuration, handler that cannot start as the first agent) would only repeat it.
- The run page, statuses and mockups would need a retry representation. Current statuses are QUEUED, RUNNING, JUDGING, COMPLETED, ERROR and STOPPED, and the mockups show no retry state or setting.

Automatic retry of errored eval attempts is deferred by design, so adding it would reverse a recorded decision.

- **Design doc:** @[design_doc:8a7aed78-e688-4d4e-8fc4-8b58c36df034|In-App Agent Evaluations] says the runner never rescues a failing attempt, because that would change the conditions being measured. It also lists automatic retries as deferred.
- **Feature requirements:** @[task:24aa8d29-3219-4d0e-b3dc-62ffdc7d1fce|Agent Evaluations] has no retry requirement. Errored repeats are named and left out of averages.
- **Launch contract:** @[contract:afba3989-faf6-4776-ae15-ddbc8fb11b9b|Eval run launch] fixes one recorded attempt per case, setup and repeat. A retry has to live inside one recorded attempt, and that choice isn't made anywhere.
- **Existing answer:** Repeats (@[task:a0556f25-88ec-48b6-a3b7-3111e9730364|Let an eval run repeat each case and setup several times, and summarise the repeats]) address variance, not errors.

The graph doesn't settle four things:

- Which errors should retry?
- Does retry apply per run or always?
- Do the failed tries stay visible?
- How do retried results count in the comparison averages?
