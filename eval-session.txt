  ## What "relevant surrounding graph" means
  
  Take a task that reads *"add a button that calls `POST /widget` with `{ type: "widget", title }`"*. Read literally it is a button and a fetch; inside a project it is rarely only that. The button may inherit the design system's component and accessibility conventions; the endpoint may return a `processingId` — making the action *pending*, pulling in an "in progress" toast and a contract for resolving the result; `type: "widget"` may trigger a backend Step Function with its own lifecycle. Any, all, or none of these hold — your job is to surface which, from the requirements, contracts, and design docs that already own those decisions, not to guess and not to reverse-engineer them from code.
  
  Relevance is judgment, not a checklist. A node earns a place in the frame only when the analysis would be poorer without it. Examples of the kind of connection worth pulling in:
  
  - **A UI task sitting under a backend feature.** The structural parent is backend, but the work is frontend, so the project's UI-practices feature carries the conventions that actually apply. Pull that UI-practices feature in (or, if it's a sprawling design doc, extract just the slice that applies and mark the node `contentSource: 'extracted'`) so the frame surfaces the rules the implementation will be judged against.
  - **A backend task that defines an API.** Walk to the consuming frontend feature whose contract the task must satisfy. The frame should show the consumer, not just the producer, so the analysis can talk about whether the proposed shape actually serves the caller.
  - **A task that supersedes a prior one.** Pull in the predecessor (and its design doc if it carries the decisions being reversed) so the analysis can speak to what's changing and why, instead of presenting the new work in isolation.
  
  These are illustrations of the move, not the only shapes that qualify. The discipline is the same in every case: a connection earns space when removing it would degrade the analysis.

  ## Current state and user attention
  
  Agent Session surfaces compose two concepts. They never treat Run phase, Agent Session current state, and output attention as three competing signals.
  
  | Concept | Scope | Values and examples | Resolution |
  |---|---|---|---|

  @[feature:6fd245bc-6474-49ee-8d0a-1d013095db8b|Run Current State] owns the effective active Turn state. Conversation-scoped phase delivery and Agent Session-keyed `currentState` delivery are projections of that same state, not independent product concepts. Session surfaces consume the canonical Agent Session `currentState`; they do not render or rank a conversation phase beside it.
  
  Shared actionable terminal states express that the session or workflow still needs action and remain until that action resolves. User attention expresses whether one user has seen a result. `MESSAGE_READY` is the generic informational completion marker: it may coexist with any shared current state, including a later Turn's active state, and opening the session may clear it only for that user.   ## User Interactions
  
  **Context access.** When a session is attached to an entity, the session surface keeps that entity reachable throughout the conversation. The attachment is part of session scope, not a prompt-only detail.
  
  **Interaction model.** Users can send follow-up messages at any time, including while the agent is mid-turn or its CLI is offline. Each message is saved once. A message the agent can take straight away is not shown as queued; one that has to wait behind earlier work shows as queued until the agent starts on it. Either way, it moves into the conversation only when the agent starts on it. Queued messages run one turn each, in the order they were sent. A queued message can be cancelled until the agent starts on it, and it shows as cancelled only once the CLI confirms the cancellation. The queue survives reloads and CLI restarts.
  
  **Read-only fallback.** When a session's runtime is unavailable, the user can still open the session and read the conversation history. Runtime-dependent controls are withheld until the session can be driven again.

⎿ DIAGRAM 22f41592-b675-41f4-b461-d8cd56e639da "Eval Batch Run" kind=PROCESS level=OVERVIEW
      Process overview of one In-App Agent Evaluations batch, from approved cases to a configuration comparison, as designed in @[design_doc:8a7aed78-e688-4d4e-8fc4-8b58c36df034|In-App Agent Evaluations]. Kind PROCESS, level OVERVIEW.
      
      Launch records the run (a copy of each case's content, items, request, handler, configurations, judge setup, rubric and run settings) but starts nothing; the app starts the eval session when the user presses Run, and that start must match what launch recorded. The run reads the live project; it is not a frozen copy. A fixed runner, not an AI coordinator, starts every case/configuration pair as its own ordinary inert Run, at most the recorded number at once, and stops an attempt only for a limit the user set or when the user stops the run. The handler keeps its normal Project Assistant preparation. Throughout the evaluated attempt, execution context excludes Eval and Eval Case definitions and grading reports from discovery and reads, including preparation and nested children, so the handler never sees grading expectations. This is the isolation boundary for Start Fresh Attempt and Target Handler Runs, addressed by @[task:9c0927a5-8c1b-4572-b6ce-ca0d4799ca0e|Evaluated agents can find Eval and Eval Case items, including their expectations, in search]. Ordinary sessions and eval authoring keep their access. Judge Attempts remains separate and receives the case and rubric through its own payload, preserving its existing exclusion from live eval-report reads. Attempt outputs are kept as evaluation evidence that can be read but not approved, applied, or fed into project search. Judging runs separately from the attempt, and human review is a separate record.
      
      The screens are shown in the Eval Page, Eval Run Page, and Eval Results Page Mockups. Child launch internals are detailed in the existing @[diagram:23d3f70d-3d92-42f6-8b43-33515852e7d0|Child Agent Launch (target)] Diagram and are not repeated here.

  analysis: I researched your question — "if an eval attempt errors, can we automatically retry it twice and use the successful retry in the comparison?" — against @[feature:24aa8d29-3219-4d0e-b3dc-62ffdc7d1fce|Agent Evaluations]. Short version: this is a change to a deliberately settled design stance, not a gap. Automatic retries are currently designed out, in several places, and the change touches a launch contract.
    
    ## What governs this
    
    - **Design intent says no retries.** @[design_doc:8a7aed78-e688-4d4e-8fc4-8b58c36df034|In-App Agent Evaluations] says the runner "does not try to rescue a stuck or failing attempt. Intervening would change the conditions of the attempt being measured. An error is recorded against its attempt and the other attempts continue; rerunning is a new attempt the user chooses to start." It also says "Do not center this design on automatic retries", lists "automatic retries" under Deferred, and says errors are shown "without introducing a failure-centric product flow". Its reasoning is measurement validity. Retrying and picking the success is a selection effect on the measured agent.
    - **The runner is built that way.** @[task:417c00ca-a311-4ed0-8439-3f287a12cd17|Run each case through its real handler in isolation, then measure and judge it] (COMPLETED) states "No retries" and "never retries or intervenes". The same text appears on the Eval Runner element of @[diagram:22f41592-b675-41f4-b461-d8cd56e639da|Eval Batch Run]. That diagram's loop has no retry branch. The code is `cli/src/agents/run-eval/eval-runner.ts`: a worker pool over the recorded attempts, with `eval-report-recorder.ts` writing the results.
    - **Today's error handling.** An errored attempt is `ERROR` and shown beside its cell. A judge failure is `ERROR` with code `JUDGE_FAILED`, and it keeps the target measurement. Limit and user stops are `STOPPED` with a `stopReason`, which is a different state. @[task:a0556f25-88ec-48b6-a3b7-3111e9730364|Let an eval run repeat each case and setup several times, and summarise the repeats] (COMPLETED) already says errored and stopped repeats are "named and left out of averages". The recognition count is "correct out of finished attempts", and measures carry "how many attempts reported" them. A retry feature changes how an errored attempt is represented and what the comparison includes. It is not purely additive.
    - **Launch contract.** @[contract:afba3989-faf6-4776-ae15-ddbc8fb11b9b|Eval run launch] (ACTIVE) records one EVAL_ATTEMPT per case, setup and repeat. The attempt report's id is the attempt's identity. The later start is accepted only with exactly those recorded attempts. If a retry is a new attempt record created at run time, it conflicts with this. If it stays inside one recorded attempt, the contract is untouched but the attempt record needs to hold the tries. @[contract:917e9c8b-9eeb-4d22-8d71-a71ac549040d|Run Eval handler admission] is unaffected.
    - **Isolation and per-attempt state.** Each attempt has its own API-prepared session and conversation (@[task:d99242e3-12e9-4889-9b89-23d97a02b0ee|Run each eval attempt as a full inert session]). Each retry must also be a fresh Run that sees no prior try's output, which the Execution requirements require for repeats.
    - **Measurement.** The Measurement requirement says time, tokens, tool calls and cost belong to the tested agent for each case and configuration, with unmeasured values shown as unavailable. A failed first try's partial usage and cost would need a home. The feature does not say whether it counts toward the attempt's totals.
    
    ## What this means for the request
    
    The outcome you want is clear: retry an errored attempt up to twice and compare using the successful one. The product consequences are not settled anywhere:
    
    1. Which errors are retried: target-handler errors, judge failures (`JUDGE_FAILED`), start or infrastructure failures. Whether `STOPPED` is ever retried (the design says a limit or a user stop is deliberate, so likely not).
    2. Whether a retry is the same recorded attempt with several tries or an additional attempt. This decides whether the Eval run launch contract and the "exactly the recorded attempts" rule change.
    3. How the comparison and expanded row show it: that the number came from try 2 or 3, how failed tries stay visible, and what happens when all three fail (it should remain an `ERROR` beside the cell).
    4. Whether failed tries' time, tokens and cost count toward the attempt's measures. Interaction with repeats: a retried repeat that succeeds counts as a finished repeat; one that never succeeds stays excluded as today.
    5. A caveat for the written design: retrying until success biases comparisons toward flaky configurations that eventually pass. This is the stated reason for the "no rescue" rule. Showing the retry count beside the result would keep it honest.
    6. Whether the limit is a fixed 2 or a run setting recorded at launch like repeats. A run setting would extend `EvalRunSettings` and the launch contract's recorded settings.
    
    ## Contract handoff
    
    No Contract exists for the runner's no-retry behaviour. It is design intent and ordinary process flow in the Eval Batch Run diagram, not a Contract. If retries are added, the promise that "launch records every attempt that will run" is the one existing Contract at risk (Eval run launch). Nothing else is a Contract candidate here.

  1. Which errors are retried: target-handler errors, judge failures (`JUDGE_FAILED`), start or infrastructure failures. Whether `STOPPED` is ever retried (the design says a limit or a user stop is deliberate, so likely not).
  2. Whether a retry is the same recorded attempt with several tries or an additional attempt. This decides whether the Eval run launch contract and the "exactly the recorded attempts" rule change.
  3. How the comparison and expanded row show it: that the number came from try 2 or 3, how failed tries stay visible, and what happens when all three fail (it should remain an `ERROR` beside the cell).
  4. Whether failed tries' time, tokens and cost count toward the attempt's measures. Interaction with repeats: a retried repeat that succeeds counts as a finished repeat; one that never succeeds stays excluded as today.
  5. A caveat for the written design: retrying until success biases comparisons toward flaky configurations that eventually pass. This is the stated reason for the "no rescue" rule. Showing the retry count beside the result would keep it honest.
  6. Whether the limit is a fixed 2 or a run setting recorded at launch like repeats. A run setting would extend `EvalRunSettings` and the launch contract's recorded settings.
  
  ## Contract handoff
  
  No Contract exists for the runner's no-retry behaviour. It is design intent and ordinary process flow in the Eval Batch Run diagram, not a Contract. If retries are added, the promise that "launch records every attempt that will run" is the one existing Contract at risk (Eval run launch). Nothing else is a Contract candidate here.
