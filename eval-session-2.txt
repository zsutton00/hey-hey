## What "relevant surrounding graph" means

Take a task that reads _"add a button that calls `POST /widget` with `{ type: "widget", title }`"_. Read literally it is a button and a fetch; inside a project it is rarely only that. The button may inherit the design system's component and accessibility conventions; the endpoint may return a `processingId` — making the action _pending_, pulling in an "in progress" toast and a contract for resolving the result; `type: "widget"` may trigger a backend Step Function with its own lifecycle. Any, all, or none of these hold — your job is to surface which, from the requirements, contracts, and design docs that already own those decisions, not to guess and not to reverse-engineer them from code.

Relevance is judgment, not a checklist. A node earns a place in the frame only when the analysis would be poorer without it. Examples of the kind of connection worth pulling in:

- **A UI task sitting under a backend feature.** The structural parent is backend, but the work is frontend, so the project's UI-practices feature carries the conventions that actually apply. Pull that UI-practices feature in (or, if it's a sprawling design doc, extract just the slice that applies and mark the node `contentSource: 'extracted'`) so the frame surfaces the rules the implementation will be judged against.
- **A backend task that defines an API.** Walk to the consuming frontend feature whose contract the task must satisfy. The frame should show the consumer, not just the producer, so the analysis can talk about whether the proposed shape actually serves the caller.
- **A task that supersedes a prior one.** Pull in the predecessor (and its design doc if it carries the decisions being reversed) so the analysis can speak to what's changing and why, instead of presenting the new work in isolation.

These are illustrations of the move, not the only shapes that qualify. The discipline is the same in every case: a connection earns space when removing it would degrade the analysis.

● I've submitted the research report for the estimate (story points) request. Two source reads were incomplete: the Work Item Types record and the edge dumps were too large to read in full, and the Decision's body was never returned.

- **Closed scalar list:** The work-item type registry only allows two declarable scalar fields, `dueDate` and `tag`. Status, priority and assignee are fixed columns. An estimate has to be added as a generic scalar through the OpenAPI spec, then the registry, then regeneration. A STANDARD-only code path would break the rule that type-specific behavior goes through the generic work-item interface.
- **Page editing:** @[feature:74f5c98b-503a-47da-98f6-74ed14d8103b|Work Item Editing] says the edit page shows only the scalars the resolved type definition declares. It must also show nothing type-specific until that definition has loaded. The estimate input should come from the declaration, not be hard-coded.
- **Cards:** I found no requirement defining what a card shows. The existing metadata controls only cover status, priority, due date and assignee.
- **Which types get it:** Whether FEATURE and GOAL show an estimate is not settled. Lifecycle fields for them are currently suppressed by hard-coded behavior (backlog task ac58e79b-a9c6-479d-8b6c-1c3f8fb3d93c).
- **Downstream effects:** The graph and embeddings services both consume work-item events built from shared OpenAPI schemas. A new field means those event schemas have to change first, and @[feature:cbd6942e-5a36-4d65-9d54-845289910558|Events System] is the feature that owns them. An existing eval case describes this exact request shape and expects those consumers to be named.
- **Unread Decision:** An active Decision (cf64a2d2-e523-4af2-ae4a-b2c7f50e87f8) says product data lives in core entity types, never in purpose-built tables or columns. I couldn't read its body, so I don't know whether a new estimate column is allowed. That needs checking before choosing storage.

I flagged two open choices in the report: which types carry an estimate and what values are allowed, and how it is stored. I made no changes to the graph.
